01

Mentalkiz

Plateforme de santé mentale scolaire

2024 En production

Application React + Supabase + microbackend NodeJS de suivi et soutien psychologique des particuliers. La difficulté principale du projet a été de mettre en place un double système permettant à la fois aux utilisateurs d'utiliser facilement les programmes, de suivre leurs infos et stats tout en permettant à des consultants du milieu médical de pouvoir créer tout ce contenu sans aucune connaissance technique.

L'optimisation était un facteur clé, que ce soit pour le nombre de requêtes ou le traitement des données qui, vu l'architecture utilisant supabase avec React, reposait en bonne partie sur le côté client. La mise en place d'outils avancés de react, comme la memoization, le choix de design patterns pour simplifier le déploiement et l'implémentation des derniers systèmes de state management furent nécessaires.

Les discussions pour déployer le projet dans les établissements scolaires et de santé d'Île-de-France étant en cours, la sécurisation des données personnelles est au coeur du projet. Un système robuste de chiffrage des données avec un double système de clé de chiffrement a été mis en place pour s'assurer que nul, pas même nous ne puissions récupérer des données sensibles.

02

kEy-sport

Géolocalisation indoor en temps réel

2026 Phase MVP

Un CEO d'équipe esport n'a aucun moyen d'engager directement sa fanbase entre les matchs. Les réseaux sociaux sont fragmentés, les apps de suivi génériques n'ont aucune identité, et les fans passifs ne reviennent pas. L'objectif était de construire une app white-label déployable pour n'importe quelle structure esport, en commençant par Mandatory (Valorant, WoW) — avec un système d'engagement communautaire autour des prédictions de matchs.

Le premier défi technique était de permettre une personnalisation poussée par équipe sans dupliquer la codebase. J'ai mis en place un système de configuration typé (TeamConfig) qui centralise le thème, les feature flags et les contenus par équipe. Chaque build Expo pointe vers une config différente via EAS Build, ce qui génère des apps store séparées à partir d'une seule codebase. Les feature flags permettent d'activer ou désactiver des fonctionnalités entières par équipe sans condition dans le code métier — les composants lisent la config via un hook useTeamConfig() et s'affichent ou non en conséquence.

Plutôt que d'intégrer une API esport payante (PandaScore à 500€/mois, inutile pour un MVP), j'ai construit une Cloud Function TypeScript planifiée qui appelle l'API MediaWiki de Liquipedia toutes les heures, parse les tableaux de matchs via node-html-parser, normalise les données dans un format interne, et les écrit dans Firestore. L'app mobile ne touche jamais Liquipedia directement — elle lit uniquement Firestore. Ça garantit zéro dépendance externe côté client, un coût API nul pendant la phase de validation, et une migration transparente vers un feed payant si nécessaire.

La logique de points est entièrement serverside via Cloud Functions Firebase pour éviter toute possibilité de triche côté client. Une fonction se déclenche sur la mise à jour du statut d'un match vers finished, compare le résultat aux prédictions enregistrées dans Firestore, et distribue les points en batch. Le leaderboard est recalculé en temps réel via un listener Firestore côté app.

03

Indoor Geolocation

Géolocalisation indoor en temps réel

2023 Terminé

Création, dans une équipe déjà formée, d'une application web de suivi en temps réel d'objets marqués par des tags dans des bâtiments.

L'objectif ici était à la fois de parvenir à gérer un flux de données conséquent et à l'optimiser tout en affichant dans des plans la position de chaque objet, gérer les états d'alerte, les pertes de contact avec le matériel. Chaque objet suivi était marqué d'un tag et des balises marquant la salle permettaient de les localiser avec une précision de moins d'un mètre. Ensuite, l'API de motorolla permettait de récupérer les coordonnées relatives de chaque objet pour pouvoir les mettre sur le plan.

L'interface devant bouger en temps réel et gérer des données précises avec des timings serrés, il a fallu travailler à la fois sur le backend php pour gérer la récupération des données et aussi sur l'opti du front pour qu'aucun temps de chargement ou problème d'affichage ne fausse le suivi d'objets parfois critiques.
